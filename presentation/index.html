02
The Problem

Casablanca: 4M people, zero shared mobility data

  • No shared data layer — grand/petit taxis & minibuses run with no GPS, booking, or schedule
  • Demand blindness — drivers cruise empty; riders wait with no visibility
  • No interoperability — ONCF rail, BRT and taxis share no data or ticketing
  • Cash-only — no trip history, no analytics, no personalization
  • Underserved periphery — Bouskoura, Sidi Moumen grow faster than routes
The core problem is not a shortage of vehicles — it is the absence of a data layer connecting supply to demand.
Every pain point here is a data problem, not a vehicle problem.

Solution & Objectives

Treat urban mobility as a data-engineering problem

Architecture · v2 — Kappa, Kafka is the single source of truth
The full system map: Producers → Kafka (KRaft) → 3 Flink jobs → Cassandra serving state → Grafana/FastAPI. MinIO is the S3 data lake; Spark is offline batch+ML only; Kafka is replayable — that's Kappa, not Lambda. 16 containers on taasim-net.

Zone Remapping · Step 2

The A–E activity score — a weighted multi-source formula

FeatureSourceWeight
Population density ρHCP 2024 census0.40
Commerce weight cGlovo0.30
POI diversity dGlovo0.20
Transit hubs tOpenStreetMap0.10

09
Porto Simulation Strategy

Warping real GPS onto Casablanca roads

  1. LOAD — Porto polylines; filter 1.5–18 km, 3–30 min
  2. SAMPLE — stratify by length → 500 trips
  3. ASSIGN — A–E transition matrix → zone by population
  4. AFFINE — linear Porto bbox → Casa bbox (cahier transform)
  5. ANCHOR — pull to centroid (α=0.80) + jitter σ≈160 m
  6. OSRM — route on real Casa street network
  7. PERSIST — curated_trajectories_v4.parquet
Why OSRM over in-process A*: zero zigzags, full OSM driving profile, no 400 MB graph in memory, cached for warm re-runs.
Live map: notebooks/casablanca_trajectories_v4.html
Porto gives authentic motion; OSRM routes it along actual Casablanca streets using OSM road data.

Warped GPS Routes on Casablanca Roads
Real Porto motion affine-mapped and OSRM-snapped onto Casablanca streets.
OSM gives shapes/transit/roads; HCP+Glovo give activity tiers; NYC sets the timing. Origin weight = population × A–E multiplier; destinations sampled from adjacent tiers for realistic cross-city flow. Eight validation panels confirm the synthetic stream behaves like real Casablanca demand.

Week 1 · Deep Dive

Two producers replay Casa traffic into Kafka

  • vehicle_gps_producer.py → raw.gps, key=taxi_id
    • COUPLED: interpolate along OSRM polyline, ±20 m noise, 5% blackout, road-snap
    • H3 res-9 → zone, ring fallback r=1..5
  • trip_request_producer.py → raw.trips, key=origin_zone
    • Hourly multiplier (peaks 08/18), petit/grand split, MAD tariffs
  • Wire: JSON, acks=all, retries=3
Coupled mode pairs each trip with a real routed polyline so taxis move on actual streets. Keys let Flink keyBy without reshuffle.

Week 3 · Real-Time

Three PyFlink jobs turn raw events into serving state

  • Job 1 · GPS Normalizer — raw.gps → validate, dedup, H3 zone, road-snap/anonymize → vehicle_positions + processed.gps
  • Job 2 · Demand Aggregator — processed.gps + raw.trips → 30 s tumbling windows → demand_zones
  • Job 3 · Trip Matcher — keyBy zone, MapState, adjacent fan-out + dedup → trips
  • Checkpoints: RocksDB, EXACTLY_ONCE, 60 s → MinIO
  • Watermarks: 3-min (Job 1); 10 s + idleness (Jobs 2/3)
Watermarks let Flink emit correct windows even when pings arrive late. cassandra-driver execute_async, not the official connector.

Week 3 · Deep Dive

Sub-second matching + privacy by design

  • Cost: 0.7·haversine_km + 0.3·idle_bonus
  • Adjacent fan-out: neighbours compete in parallel; first free taxi wins via shared Set<trip_id> dedup
  • Match P95 ≈ 1.2 s (target < 5 s)
  • Anonymization: snap to centroid + hash jitter — raw lat/lon never persisted

Week 6 · Feature Engineering

Build a leakage-free feature matrix (183,981 rows)

  • Input: s3://curated/trips/ → Output: s3://mldata/features/
  • Target: demand = trips per zone per 30-min slot (48 slots/day)
  • Features: hour_of_day, day_of_week, is_weekend, is_peak, slot_of_day, zone_idx, demand_lag_1d, demand_lag_7d, rolling_7d_mean
The critical fix: an earlier draft included supply and supply_demand_ratio — both from the same 30-min slot as the target → label leakage. Removed both; kept only retrospective lag/rolling features. Temporal split (not random) at 2014-05-01.
We caught and removed label leakage. Temporal split, not random, because it's a time series.
